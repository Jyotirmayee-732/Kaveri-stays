Three things describe this API:

05_openapi_final.yaml — the API contract/specification.
The OpenAPI specification generated by FastAPI — the specification generated from the FastAPI application.
The Postman collection — used for testing the API endpoints.

Authoritative source: 05_openapi_final.yaml is the authoritative API contract.

To prevent the other two from drifting, any API change should first be reflected in 05_openapi_final.yaml. The FastAPI implementation and Postman collection should then be updated and tested against this contract. This keeps all three descriptions synchronized.



## 7.2
Property scoping belongs in a dependency because it is an authorization rule that should be applied consistently before database queries run. A reusable dependency prevents the same property-access logic from being duplicated across multiple endpoints and reduces the risk of accidentally exposing data from another property.

## 7.8
Authorization should be checked before executing the database query whenever the endpoint is simply determining whether the user has access to the requested resource. This prevents unauthorized users from accessing data they should not see.

For object-level ownership, the authorization condition should be included inside the SQL query as a WHERE clause when possible. For example, a guest requesting a booking should query only rows where guest_id matches the authenticated guest. This is the only correct approach when the existence of another user's resource must not be revealed.

Therefore, role authorization can happen before the query, while ownership and data-level scoping should be enforced inside the query.
